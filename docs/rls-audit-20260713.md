# RLS audit — 2026-07-13 (token read isolation)

Supersedes the read-model section of `rls-audit-20260709.md`, which recorded
`SELECT ... USING (true)` as "a deliberate collaborative-read model". That
model leaked private drafts and is now closed.

## Finding (HIGH, confirmed empirically)

`SELECT` on `tokens` and its child tables was `USING (true)` for every
authenticated user. Only writes were owner-scoped. A disposable second
account, created for the audit, could read:

| What | Before | After |
| --- | --- | --- |
| Another owner's `draft` tokens | 6 | **0** |
| Their allocations / supply metrics / stat history | 6 / 1 / n | **0 / 0 / 0** |
| Own draft (non-regression) | 1 | **1** |
| Validated tokens + children (non-regression) | 12 / 5 | **12 / 5** |

The `kg_*_v1` views are `security_invoker` and carry no status filter, so
they inherited the same leak: other users' drafts appeared in the knowledge
graph. Fixing the base tables fixed the views transitively, with no view
change.

## The rule

Migration `20260723_scope_token_reads_to_visible_set.sql` defines the visible
set **once**:

```sql
public.readable_token_ids() =
      status IN ('in_review', 'validated')   -- submitted to the community
   OR created_by = auth.uid()                -- my own work, at any status
   OR public.is_moderator(auth.uid())        -- review duty
```

Every read policy on these ten tables delegates to it: `tokens`,
`allocation_segments`, `supply_metrics`, `emission_models`, `data_sources`,
`risk_flags`, `claim_sources`, `vesting_schedules` (via its allocation),
`token_stat_history`, `intuition_publish_runs`.

**`in_review` is visible on purpose.** It is a submission, not a private
draft: `open_challenge_tx` accepts challenges against `in_review` tokens
(only `draft` is rejected) and the knowledge-graph route includes them.
Hiding it would break the community review loop. `draft` is the private
state, and that is what the migration protects.

**Extending it is one clause.** Teams, or sharing a token before
publication, land by adding a single `OR` to the function body; all ten
tables follow with no policy left behind. That is the whole point of routing
every policy through one function rather than repeating the predicate.

## Also fixed

`api/challenges/[id]/evaluate-threshold` read the challenged token's owner
with `maybeSingle()` and no error check. An unreadable row would not fail the
request: it would silently drop the owner from the stake-exclusion list and
return a **wrong** threshold verdict. It now fails loudly.

## Known-open, deliberately out of scope

Readable by any authenticated user, unchanged by this pass:

- `profiles` (display_name, role, organization — no email column)
- `user_roles` (who is a moderator)
- `wallet_links` (**user_id → wallet_address**: any account can enumerate
  every user's linked wallets. Worth a decision: attestations are public
  on-chain, but the identity ↔ address mapping is not.)
- `challenges` / `challenge_events` (community review is public by design)
- `intuition_atom_mappings` / `claim_mappings` / `provenance_mappings` (keyed
  by atom/triple id, not token_id; only ever written for submitted tokens, so
  they carry nothing about private drafts)

## How to re-verify

The cross-user probe is local-only (`tasks/rls-probe.ts`, git-ignored): it
creates a disposable confirmed user, seeds a draft it owns, and asserts the
four rows of the table above. Run it after any change to the read model.
