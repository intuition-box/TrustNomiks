**Scope:** remote Supabase project (`pnuhumbvhgmtxhvykfgy`), all objects in schema `public`.
**Method:** read-only queries via the Supabase MCP server (`pg_class`, `pg_policies`, `pg_proc`, ACLs) plus the Supabase security advisor (`get_advisors`). Nothing was modified.

## 2. Findings

### F1 — HIGH (confirmed): `kg_*` views expose the full dataset to anonymous callers

`kg_atoms_v1`, `kg_triples_v1`, `kg_triple_sources_v1` (created in `20260322_knowledge_graph_views.sql`) run with owner privileges (no `security_invoker`), bypassing RLS on the seven tables they project — including wallet addresses, contract addresses, statuses, and unvalidated drafts. Their ACLs grant **ALL privileges to `anon`** (Supabase default grants), so `GET /rest/v1/kg_atoms_v1` with just the publishable anon key returns everything, no session required. The Next.js middleware is not involved in PostgREST calls.

App-impact check before remediation: the views are consumed only by authenticated server routes (`src/app/api/knowledge-graph/route.ts:74`, `src/app/api/intuition/runs/[runId]/route.ts:151`) and `src/lib/intuition/bundle-builder.ts:100`; the public landing page tolerates blocked anonymous reads by design (`src/app/page.tsx:14`). Scripts use the service role (bypasses RLS). → `security_invoker = true` + revoking `anon` is behavior-preserving for the app.

**Fix:** migration `20260709_harden_kg_views_and_function_grants.sql` §1.

### F2 — MEDIUM: SECURITY DEFINER functions callable by `anon`

The six `save_*_tx` RPCs and `is_visualization_ready` are `SECURITY DEFINER` and executable by `anon` (advisor `0028`). Verified remotely: all six `save_*_tx` bodies check `auth.uid()` and pin `search_path = public`, so anonymous calls fail on the ownership check — defense in depth still says revoke. `is_visualization_ready` has **no auth check and a mutable `search_path`** (advisor `0011`), as does the trigger function `update_updated_at`.

**Fix:** migration §2 (revoke anon EXECUTE) and §3 (pin `search_path`).

### F3 — MEDIUM (open, product decision): `intuition_pin_cache` writable by any authenticated user

Policies `INSERT WITH CHECK (true)` and `UPDATE USING (true) WITH CHECK (true)` (advisor `0024`) let any signed-in user overwrite any cache row (IPFS pin statuses) — a cache-poisoning vector between contributors. Acceptable while all users are trusted; before opening the platform (Roadmap "Community curation"), either add a `created_by` scope or move writes behind a server-side context.

### F4 — LOW: leaked-password protection disabled

Supabase Auth is not checking passwords against HaveIBeenPwned. **Fix:** dashboard toggle — Auth → Settings → Password security ([docs](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)). Not expressible as a SQL migration.

### F5 — INFO: default privileges keep granting to `anon`

New tables/functions/views in `public` get `anon` grants by default, which is how F1/F2 arose. RLS-with-no-anon-policy contains tables, but views and functions are only guarded by grants. Recommendation for a later migration: `ALTER DEFAULT PRIVILEGES` to stop auto-granting to `anon`, or make the F1/F2 checks part of the new-migration checklist.

### Addendum — post-remediation check (same day)

After applying the migration, the advisor confirmed the three `security_definer_view` ERRORs are gone. The `0028` WARNs persisted: Postgres grants function EXECUTE to `PUBLIC` by default and `anon` inherits from it, so revoking `anon` alone was ineffective (verified: `pg_proc.proacl` still showed `=X/postgres`). Follow-up migration `20260709_revoke_public_execute_definer_functions.sql` revokes EXECUTE from `PUBLIC`; `authenticated`/`service_role` keep their explicit grants.

Verified after applying the follow-up: all seven function ACLs are now `{postgres, authenticated, service_role}` only, and every `0028` WARN is gone. Remaining advisor items are exactly the accepted set: `0024` pin cache (F3, product decision), `0029` authenticated EXECUTE on definer RPCs (intentional — bodies enforce ownership), and the Pro-plan-only leaked-password toggle (F4).
